# Contributing to opencode-harness-kit

Thanks for looking. This is a small project and the bar for a change is that it
is either verifiable or it does not land.

## Before you start

`npm run check` must pass on an untouched checkout. If it does not, that is a
bug worth its own issue — do not build on top of a red baseline.

## What a change has to come with

The test suite is the contract, so a change without a test is a change nobody
can trust:

- **Model routing, effort tiers, pruning, retention.** Add an assertion to
  `test/`. These tests run offline and must stay offline: no network, no model
  calls, no API keys. `npm test` has to pass on a machine that has never seen
  an OpenCode login.
- **A new command or flag.** `oc-harness <flag>` that the docs do not mention
  will be found by nobody, and `oc-harness help` listing a command that does not
  exist is worse.
- **A changed number.** If your change moves a number a profile claims —
  effort, context budget, token budget — the README has to change with it, in
  the same commit. A stale number in the README is a bug, not a nit.
- **Anything that writes to disk.** It needs a `--dryrun` path, and it must keep
  a backup. `~/.config/opencode/` is a live config for anyone who runs it,
  including the people reviewing your PR.

## Running the checks

```bash
npm run check        # build + typecheck + tests + live install + verify
npm test             # the offline assertions, fast
npm run typecheck
```

`npm run check` performs a real install into `~/.config/opencode/` and then
verifies it. If you are not comfortable with that over your own config, run the
layers individually and say so in the PR.

`eval/ab.mjs` and `npm run measure` spawn real agents and cost real tokens.
They are deliberately not part of `npm run check`, and a PR does not need them.

## House rules

- Node 22 or newer. The CLI uses `node:` prefixed builtins, so an older Node
  fails at import time rather than with a useful message.
- No new runtime dependencies without a reason that survives review. A CLI that
  installs is one a lot of people will not install twice.
- `dist/` is committed because the release tarball needs it. It is generated by
  `npm run build`; never hand-edit it, and never commit it without rebuilding.
- Match the surrounding comment style: comments explain **why**, especially
  where the obvious version would be a trap.

## Pull requests

Keep the diff to one concern. Say what you changed, what you measured, and what
you did not check. If you fixed a bug, the PR should fail before it and pass
after — say which test does that.

Bump nothing by hand in `package.json`: releases are cut by tagging `v*`, and the
`publish` job reads the version from there.

## Cutting a release

```bash
# 1. the version and the changelog entry
npm version minor            # or major, or patch
$EDITOR CHANGELOG.md        # the entry for the new version

# 2. the tag, which is what triggers the publish
git commit -am "release: <version>"
git tag -a v<version> -m "<what the release is>"
git push origin main v<version>
```

The tag triggers the workflow, the tests run, and the `publish` job publishes
the tarball.

### How the publish authenticates

Two ways, and the job picks whichever is available:

**Trusted publishing (OIDC)** — the default, and what the repository is set up
for. There is no npm secret in the repository at all: npm exchanges the
runner's OIDC identity for a short-lived publish token scoped to the workflow.

**A token** — the fallback, for when OIDC is not set up. Set the `NPM_TOKEN`
repository secret to a granular token scoped to `opencode-harness-kit` with
**Read and write** on the package. If the secret is present the job uses it;
if it is absent the job uses OIDC.

```bash
gh secret set NPM_TOKEN --repo pham-canh/space-harness
```

> **`gh secret set` takes the secret NAME as its first argument**, and the
> value is pasted at the prompt. `gh secret set <the-token-value>` creates a
> secret whose *name* is the token - and the name of a secret is visible to
> everyone who can read the repository's Actions secrets list. If a secret
> ever shows up named like `npm_...`, delete it and set it again properly.

A token needs write access *on the package*, not on the account. npm answers
**404** for a package the token cannot touch, which reads like a missing
package rather than a missing permission.

### Configuring the trusted publisher

npm's web form has four fields and **npm does not validate what you type into
it** — a typo is discovered at publish time, and npm reports it as

```
OIDC token exchange error - package not found
```

which reads like a missing package. The package is there; the configuration
is not matching, and npm does not say which field.

npm ships `npm trust` for exactly this, and it can also read what is stored.
So the configuration is set from the command line, where it is compared
against the identity the workflow will actually present:

```bash
npm install -g npm@latest      # npm trust needs 11.15.0 or later
npm login                       # 2FA has to be enabled on the account
npm run release:trust           # check, and replace it if it is wrong
```

`npm run release:trust` reads what npm has stored, compares it against the
workflow's own identity, and replaces it when it differs. npm allows exactly
one configuration per package and cannot edit it, so replacing means revoking
first — the script does that.

To set it without the script, the command is:

```bash
npm trust github opencode-harness-kit \
  --file ci.yml \
  --repo pham-canh/space-harness \
  --allow-publish --allow-stage-publish -y
```

The configuration it writes is:

| field | value |
|---|---|
| Organization or user | `pham-canh` |
| Repository | `space-harness` |
| Workflow filename | `ci.yml` (the filename only, not a path) |
| Environment name | **empty** |
| Allowed actions | `npm publish` and `npm stage publish` |

**The environment name is the field that catches people.** GitHub only puts an
`environment` claim in the OIDC token when the job declares one. This
workflow declares none, so the claim is absent — and a configuration that
names an environment can never match a token that does not carry one.

The workflow is the one in `.github/workflows/ci.yml`, and the claims it
presents are printed by the publish job before it tries:

```
repository    pham-canh/space-harness
workflow file ci.yml
environment   (absent) - the trusted publisher must name NO environment
owner         pham-canh
```

A newly created trusted publisher has to complete its first successful
publish **within 2 days**, or it expires and has to be created again.

> **Both `npm trust` and `npm publish` need a one-time password**, and the
> web URL they print is masked in the log — so run them in a terminal, where
> npm prompts for the code. The token path below needs none of that.

The GitHub release is written by hand from the CHANGELOG entry:

```bash
gh release create v<version> --title "<version> - <what it is>" --notes-file <notes>
```
